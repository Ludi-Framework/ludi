Ludi es un framework web donde el código de la aplicación es Lua y el runtime
es Rust ([hyper](https://hyper.rs) + [tokio](https://tokio.rs)).

```
                    ┌────────────────────────────┐
 Clientes HTTP ──▶  │  Rust: hyper + tokio       │   ludi_core (módulo nativo)
                    │  worker threads            │
                    └────────────┬───────────────┘
                       canal mpsc (un Job por petición)
                    ┌────────────▼───────────────┐
                    │  Hilo Lua (tu app)         │   rutas, middlewares,
                    │  un solo hilo, estilo Node │   handlers — Lua puro
                    └────────────────────────────┘
```

- **Rust es solo transporte**: parsea el HTTP, aplica límites y reenvía cada
  petición por un canal. No sabe nada de rutas.
- **Todo el Lua corre en un solo hilo** — el intérprete que llamó a
  `app:listen()`. Los worker threads nunca tocan el intérprete, así que no
  hay callbacks entre hilos ni FFI.
- Cada worker de hyper espera su respuesta en un canal oneshot, así que los
  handlers lentos no bloquean el accept de conexiones.

## Modelo de concurrencia

- **El código Lua siempre es de un solo hilo.** Un handler nunca corre en
  paralelo con otro handler en la misma VM. Sin locks, sin data races en el
  código de la aplicación.
- La concurrencia viene del runtime: el I/O de sockets es paralelo en Rust.
- Cada handler corre dentro de una corrutina desde la v1, aunque nada haga
  yield todavía. Eso convierte la futura API async en un cambio no
  disruptivo.

## Ciclo de vida de la petición

1. Un worker de hyper lee la petición y aplica el límite de tamaño del
   cuerpo.
2. La petición cruza al lado Lua como una tabla simple; el router hace match
   de método + segmentos del path, extrayendo los `:params`.
3. Middlewares globales, middlewares de la ruta, handler — corren dentro de
   una corrutina, encadenados por llamadas explícitas a `next()`.
4. Los errores del handler se capturan (`pcall`): el cliente recibe un
   `500`, el error va a stderr, nunca se filtra.
5. La tabla de respuesta cruza de vuelta; hyper la escribe.

## Evolución planificada

1. ✅ VM única, API pública estable.
2. Biblioteca estándar async (cliente HTTP, SQL, filesystem) sobre el puente
   de corrutinas.
3. Múltiples workers: SO_REUSEPORT, un hyper + una VM por worker — el modelo
   cluster de Node.
4. Optimizaciones de memoria: menos copias en el camino petición/respuesta.

<Aside type="note">
	Las decisiones individuales, con alternativas y trade-offs, viven como ADRs en
	el repositorio:
	[docs/adr/](https://github.com/Ludi-Framework/ludi/tree/main/docs/adr).
</Aside>

## No-objetivos

- Exponer conceptos de Rust, tokio o mlua al código de la aplicación.
- Lua multi-hilo. El paralelismo es por VM, nunca intra-VM.
- Ser un framework MVC con baterías incluidas. Ludi es la capa HTTP.
