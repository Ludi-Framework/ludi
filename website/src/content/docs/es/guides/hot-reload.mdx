Con `LUDI_WATCH=1`, Ludi observa todos los archivos `*.lua` bajo el
directorio de trabajo y recarga la aplicación con cada cambio — sin
reiniciar, sin volver a vincular el puerto, sin interrumpir peticiones en
curso.

```bash
LUDI_WATCH=1 lua app.lua
```

Edita una ruta, guarda, refresca: el cambio ya está en vivo.

## Cómo funciona

1. Se detecta un cambio (archivo `.lua` nuevo, editado o eliminado).
2. Los módulos de la aplicación se quitan de `package.loaded`, así que
   `require` los vuelve a leer. La stdlib de Lua y el propio Ludi se
   conservan.
3. El entrypoint (`app.lua`) se vuelve a ejecutar; su llamada a
   `app:listen()` se intercepta y la app nueva reemplaza a la anterior en
   su lugar.

La recarga corre en el hilo de Lua, entre peticiones — nunca en medio de
una. Una recarga que falla (error de sintaxis, error al cargar) imprime en
stderr un extracto enmarcado del código — línea culpable resaltada, con
carets bajo el token en el que se atascó el parser — y la versión anterior
sigue sirviendo hasta el próximo cambio:

```
  reloading (app.lua changed)

  ✗ Syntax error — keeping previous version

  app.lua:12 ')' expected (to close '(' at line 10) near 'end'

    10 │ app:get("/users", function(_, res)
    11 │     res:json({ users = users })
  ▶ 12 │ end
       │ ^^^

  Fix the file and save to reload.
```

Una recarga exitosa imprime `✓ reloaded`. Los colores se desactivan con
`NO_COLOR` definido o en terminales tontas.

## Semántica

- El estado guardado en locals de módulo se reinicia con cada recarga,
  como al reiniciar el proceso.
- El callback de `listen` no vuelve a correr — el puerto se vincula una
  sola vez.
- Los archivos en directorios ocultos, `target/` y `lua_modules/` se
  ignoran.

<Aside type="caution">
	Pensado solo para desarrollo: deja `LUDI_WATCH` sin definir en producción —
	el watcher consulta el filesystem y recarga con cada escritura del deploy.
</Aside>
